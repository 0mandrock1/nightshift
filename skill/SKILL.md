# swarm — рій паралельних cc-run.sh лейнів

**1.2.0**: усунуто 12 знахідок зовнішнього рев'ю — Tier 0 заблоковано
маркером до фази 2, синтаксичний денилист verify-cmd, `cc-estimate.sh
--compare` (рій vs ланцюг) перед вибором для N=6..20, ланцюгова гілка веде
до model-router-runfile, §9 «Доставка» (retention гілок/worktree, ручний
мерж fanin), лічильник ескалацій переживає рестарт (fail-closed без БД),
`swarm.verifications` заповнюється, `{PI_DIGIT}` реально підставляється,
`bin/cc-gc.sh` для ретеншену, Telegram PREFLIGHT/FACT-блоки в `bin/cc-tg-format.sh`.

Успадковує транспорт cc-remote-agent (claude -p) і стоїть поруч з
model-router-runfile (батч-рівень). Skill body ≤ 500 рядків — деталі формату
плану й пасток нижче, без окремого references/ (обсяг не вимагає). Продукт
перенесено в `/root/projects/cc-swarm/` (власний git, MIT) — драйвери в
`bin/`, схема БД у `sql/`, тести в `tests/`. `/root/ops/cc-runs/cc-swarm.sh`
і `cc-lane-local.sh` — симлінки на `bin/*`, лишені для сумісності старих
викликів; новий код кличе `bin/` напряму.

## 0. Перед запуском — ОБОВ'ЯЗКОВО

Перш ніж спавнити рій, скіл **зобов'язаний** прогнати пре-фліт оцінку і
показати Марку блок `PREFLIGHT:` у чаті ДО запуску. Це не опція:

```
sh /root/projects/cc-swarm/bin/cc-estimate.sh --task <task.md представника лейна> \
  --model <tier рою> --lanes <N> --maxpar <MAXPAR> --run-id <swarm-id>
```

`cc-swarm.sh` сам викликає це перед спавном (пише в `swarm.log` і в стартову
нотифікацію) — але скіл друкує той самий блок явно в чаті, а не лише
покладається на лог, бо саме тут Марк вирішує, чи ціна прийнятна. Якщо
прогноз показує рядок `PREFLIGHT: ⚠ дорого` (>40% тижневого кепу) —
підсвітити це окремо і почекати підтвердження, не спиняти автоматично.

## 1. ROUTER — перша секція, найважливіша

Скіл не радить, він **обирає**. Порядок дій:

1. Порахувати 6 сигналів і надрукувати їх таблицею:

   | Сигнал | Питання |
   |---|---|
   | N | скільки незалежних одиниць роботи |
   | V | чи є на КОЖНУ одиницю машинна умова успіху (тест/парсер/grep/exit code)? bool |
   | D | чи є залежності по порядку між одиницями? bool |
   | S | чи ділять одиниці спільну ціль деплою або один файл без явного чанкування? bool |
   | J | чи потрібне судження ВСЕРЕДИНІ одиниці (смак, дизайн, вибір підходу)? bool |
   | T | типовий обсяг виводу на одиницю: малий (<300 рядків) / великий |

2. Застосувати жорсткі правила по порядку, перший збіг виграє:

   | Правило | Гілка | Причина |
   |---|---|---|
   | `S == true` | ЛАНЦЮГ (`cc-chain.sh`) | гонка за спільний ресурс |
   | `D == true` | ЛАНЦЮГ | порядок — залежність, рій його не тримає |
   | `V == false` | ЛАНЦЮГ | без машинного гейту рій виробляє сміття, яке потім читає Sonnet — дорожче, ніж зробити відразу |
   | `N < 6` | ЛАНЦЮГ | фіксований оверхед старту сесії (системний промпт + тули + CLAUDE.md) не амортизується — швидкий відсів очевидно малих N БЕЗ розрахунку |
   | інакше | РІЙ | — |

   Для `N` у діапазоні `6..~20` (не відсіяне `N<6`, але й не очевидно велике)
   `N<6` більше не остаточний висновок сам по собі: перед фінальним `ROUTE:`
   ОБОВ'ЯЗКОВО прогнати
   `sh /root/projects/cc-swarm/bin/cc-estimate.sh --compare --lanes N --maxpar MAXPAR --model <tier рою> --chain-task <task.md>`
   (ланцюг за замовчуванням — sonnet) і показати обидва рядки `COMPARE:` у
   PREFLIGHT-блоці (§0) ПЕРЕД `ROUTE:`. Оцінювач лише інформує — рішення все
   одно приймається за таблицею правил вище, але Марк бачить обидва числа
   до старту.

   Гілка ЛАНЦЮГ — не глухий кут: асистент будує plan-файл у форматі
   model-router-runfile (рядки `slug|style|task.md|model`) з тих самих
   одиниць роботи, що розглядались для рою, і запускає `cc-chain.sh` тим
   самим викликом, що описаний у скілі model-router-runfile, напр.
   `sh cc-chain.sh <repo> <chain-plan.txt> <chain-id>`.

   Tier лейна в гілці РІЙ:
   - `J == false` і `T` малий -> перевірити маркер
     `/root/projects/cc-swarm/bin/.local-tier-ready`. **Файла нема — Tier 0
     недоступний, обирай Tier 1 (`haiku`), без винятків і без запиту
     підтвердження.** Маркер існує -> Tier 0 (`local:*`, див. §2). Це
     інструкція асистенту, що читає скіл: сам драйвер (`cc-swarm.sh`) tier
     не обирає, приймає вже готове поле `model` з плану, тож перевірка
     маркера — обов'язковий крок ПЕРЕД тим, як писати `local:*` у plan-файл.
   - інакше -> **Tier 1** (`haiku`)

3. Окремий випадок — **ГІБРИД**: одиниці різнорідні (частина проходить
   машинний гейт, частина ні). Рій на однорідну підмножину + ланцюг на
   решту, ланцюг завжди ПІСЛЯ рою (щоб не блокувати паралельну частину
   послідовною).

4. Fan-in — завжди, незалежно від гілки: **Sonnet**, ніколи Haiku.

5. Надрукувати рядок рішення буквально в цьому форматі:

   ```
   ROUTE: рій|ланцюг|гібрид | N=.. V=.. D=.. S=.. J=.. T=.. | tier=.. | причина=<перше правило що спрацювало>
   ```

6. Якщо Марк наполягає на рої всупереч роутеру — виконати, але спершу
   надрукувати один рядок з тим правилом, яке порушується, і очікуваною
   ціною (наприклад: «порушено V==false -> ланцюг; рій без гейту віддасть
   N неперевірених дифів на Sonnet-читання»).

## 2. Триярусна модель ролей

| Tier | Модель | Роль |
|---|---|---|
| Tier 0 | `local:*` | Локальна квантована модель (домашній ПК, RTX 3060 12GB). Механічний гриндер там, де ретрай коштує нуль і гейт машинний. Без судження. Цінність — не швидкість (гірша за Haiku), а доступність, коли тижневий ліміт Claude вичерпаний. Стеля 2 паралельні лейни (KV-кеш, не ваги). **НЕДОСТУПНИЙ, доки нема маркера `bin/.local-tier-ready` (фаза 2 не готова).** У поточному стані бекенд `cc-lane-local.sh` — стаб, який завжди повертає `RESULT: fail`. Гілка Tier 0 лишається в документації як точка розширення (префікс `local:` у полі model уже закладений у `cc-swarm.sh`), але §1 крок 2 забороняє її обирати без маркера — план з `local:*` без маркера дасть 100% fail на кожному такому лейні. |
| Tier 1 | `haiku` | Лейни, де треба слідувати нетривіальній інструкції, але без вибору підходу. |
| Tier 2 | `sonnet` | Fan-in, завжди. |
| Opus | — | Тільки планувальник, тільки коли декомпозиція нетривіальна (§3). Ніколи лейн. |

## 3. Хто планує

Дефолт — **Sonnet**. Opus — тільки якщо сама декомпозиція нетривіальна, і
це окреме явне рішення, а не автоматика. Причина: планувальник —
найдорожчий учасник рою, а не лейни; ескалація Opus має бути свідомою.

## 4. Лейни

Haiku або Tier 0. Один лейн = один файл АБО явний непересічний
діапазон рядків/секцій одного файла. Промпт лейна:
- однорядкові кроки,
- машинна умова успіху (=verify-cmd плану),
- явна заборона ініціативи: «не рефактори сусіднє», «не чіпай нічого поза
  своїм діапазоном».

## 5. Розсіювання (seed/варіації)

Коли лейнам треба різні seed чи варіації підходу — брати цифри числа π за
індексом лейна (детерміновано, відтворювано): лейн 0 -> `3`, лейн 1 -> `1`,
лейн 2 -> `4`, лейн 3 -> `1`, лейн 4 -> `5`, лейн 5 -> `9`, ... Ніколи RNG.
`cc-swarm.sh` підставляє це автоматично: літерал `{PI_DIGIT}` у task.md
лейна замінюється на цифру за 0-indexed позицією лейна в плані ще до
`claude -p` (у скопійований `$d/task.md`, оригінал плану не чіпається).
Приклад у task.md: `Обери варіант палітри #{PI_DIGIT} з переліку нижче.`

## 6. Fan-in

Завжди Sonnet, ніколи Haiku. Порядок: спочатку машина (тести/лінт з
verify-cmd кожного лейна вже пройшли до fan-in), потім модель зводить.

**Ескалація.** Якщо fan-in каже «недороблено» — рівно ОДИН повторний рій
на залишковий скоуп. Другої ескалації нема: після неї задача віддається
одним звичайним раном. Причина жорсткої стелі: необмежений цикл
рій→фейл→рій = необмежений спалений ліміт, і немає машинного сигналу, який
би сам зупинив цикл — тільки лічильник ескалацій зупиняє.

Лічильник переживає рестарт (не in-memory) — `ESCALATION_OF=<run_id
попереднього рою> sh cc-swarm.sh <repo> <plan> <новий-id>`. Драйвер читає
`attempt` попереднього рою з `swarm.runs`: `attempt>=2` -> відмова "стеля
ескалацій вичерпана", exit 1, ще до спавну. **Якщо БД недоступна — теж
відмова** (fail-closed, не fail-open): це єдине місце у драйвері, де
відсутність телеметрії блокує ран, бо саме ця перевірка захищає ліміт.

## 7. Формат plan-файлу

```
lane-slug|task.md|verify-cmd|model|style
```

- `lane-slug` — унікальний, використовується як ім'я гілки/worktree.
- `task.md` — шлях до промпту лейна.
- `verify-cmd` — shell-команда, виконується В worktree лейна після рану;
  exit 0 = лейн зарахований. **Обов'язкова**, порожня — драйвер падає на
  старті (§8 пастки).
- `model` — дефолт `haiku`. `local:<tag>` (напр. `local:qwen2.5-coder:14b`)
  -> лейн іде в `cc-lane-local.sh`.
- `style` — дефолт `none`.

Приклад на 3 лейни:

```
lane-a|/root/ops/cc-swarms/plans/lane-a.md|grep -q "export function foo" src/a.ts|haiku|none
lane-b|/root/ops/cc-swarms/plans/lane-b.md|npm test -- b.spec.ts|haiku|none
lane-c|/root/ops/cc-swarms/plans/lane-c.md|test -f dist/c.json|local:qwen2.5-coder:14b|none
```

Fan-in файл — `<swarm-plan>.fanin`, той самий формат task.md, без полів
плану:

```
Зведи результати лейнів lane-a, lane-b, lane-c (див. INBOX.tsv у корені
worktree — маніфест лейнів з exit-кодами). Провір, що зміни не конфліктують
по сенсу (не лише по git merge), прожени фінальний build. RESULT: ok|fail.
```

Виклик драйвера:

```
sh /root/projects/cc-swarm/bin/cc-swarm.sh <repo> <swarm-plan> <swarm-id>
```

(старий шлях `/root/ops/cc-runs/cc-swarm.sh` — робочий симлінк, обидва
еквівалентні). `DRYRUN=1`, `MAXPAR=N`, `LANE_TIMEOUT=секунди` (дефолт
1800) — env-перемикачі, див. `bin/cc-swarm.sh` header.

## 7b. Телеметрія — що записується

Кожен ран (одиночний, ланцюговий крок, лейн, fan-in, сам рій) пише рядок у
Postgres, схема `swarm` у БД `mandrock_kb` (`sql/001_swarm_schema.sql`,
best-effort — недоступна БД ніколи не валить ран):

| Таблиця | Що з неї дістати |
|---|---|
| `swarm.runs` | вартість (токени/час) будь-якої одиниці за kind/model/status; `parent_run_id` зв'язує лейни з роєм — звідси "скільки коштував увесь рій" (sum по parent_run_id) |
| `swarm.estimates` | `predicted_*` vs `actual_*` (дописує `cc-telemetry.sh` після факту) -> `error_pct` — наскільки помиляється оцінювач, накопичується сама історія калібрування |
| `swarm.routes` | зафіксовані рішення роутера §1 (route/tier/rule_fired/human_override) — доказ, що роутер реально економить, а не просто теоретизує |
| `swarm.verifications` | лог verify-cmd по лейнах (поки не заповнюється жодним скриптом — точка розширення) |

Модель у `swarm.runs`/`swarm.estimates` нормалізована до tier-шорткату
(`sonnet`/`opus`/`haiku`), не до повного ідентифікатора моделі — саме так
`cc-estimate.sh` матчить медіану.

## 7c. Таймаут і повторний запуск

- **`LANE_TIMEOUT`** (дефолт 1800с) — лейн, що не вклався, вбивається
  через `timeout`; у маніфесті отримує статус `timeout` (рахується як фейл
  для загального результату рою, але НЕ блокує інші лейни, на відміну від
  `limit`).
- **Повторний swarm-id.** Драйвер на старті робить `git worktree prune` і
  відмовляється, якщо `$SWARM_DIR/<slug>` вже зайнята з попереднього рою —
  явна відмова з поясненням, не мовчазний масовий fail. Обери інший
  swarm-id або прибери стару теку вручну.

## 8. Пастки

- **Read-only аудит-лейни й контракт `RESULT: ok|fail`.** Для задач, де
  сам сенс лейна — винести вердикт (design-compliance аудит, лінт-звіт,
  perf-профіль), `RESULT: fail` семантично конфліктує з "лейн не
  доробив": `cc-run.sh` трактує будь-який `RESULT: fail` як провал рану
  (exit 2, ❌-нотифікація), навіть коли звіт написаний повністю й
  правильно, а `fail` — це коректна відповідь на "чи компліантний
  застосунок". Перевірено 02.09 на design-audit-рої (11 лейнів): усі
  10 non-compliant лейнів дали ❌ в телеграм при 100% виконаній роботі —
  шум, не сигнал. Для audit-типу задач не використовувати голий
  `RESULT: ok|fail` як носій вердикту; або (а) task.md явно каже
  `RESULT: ok` завжди при завершеному аудиті незалежно від знахідок, а
  вердикт — окреме поле в самому звіті (`## Verdict: compliant|non-compliant`),
  або (б) прийняти шум як норму для цього класу свормів і не плутати
  ❌-хвилю нотифікацій із реальним провалом рану — звірятись з
  reports/*.md, не з manifest.tsv/телеграмом.

- **Спільна ціль деплою.** Два лейни, що пишуть у той самий deploy-таргет
  чи не-чанкований файл -> `S==true` -> мало бути ланцюгом, не роєм.
- **verify-cmd без машинної умови.** `cc-swarm.sh` перед спавном ловить
  синтаксичний денилист очевидного самообману: точний збіг (після trim) з
  `true`/`:`/`exit 0`/`echo ok`/порожнім рядком, і голий `echo` без
  подальшого `&&`/`;`/`|` іншої команди. Збіг -> план невалідний, ніхто не
  спавниться, та сама помилка, що й для порожнього verify-cmd. Це НЕ повна
  перевірка (неможливо синтаксично довести довільну команду — гейт), лише
  відсів очевидного; вигадливіший самообман (`test -f /tmp` без стосунку до
  роботи лейна) денилист не ловить — це лишається людському рев'ю плану.
- **Лейн, що читає скіли.** Лейн Haiku/Tier 0 не повинен відкривати
  `~/.claude/commands/` чи інші SKILL.md — це контекст планувальника, не
  лейна; роздування контексту на лейн = та сама причина, з якої попередній
  прогін цієї задачі здох на 1M input.
- **Рій на задачі де лейнів < 6.** Оверхед старту сесії (системний промпт +
  тули + CLAUDE.md) на кожен лейн не амортизується — `N<6` завжди ланцюг.
- **Полінг замість нотифаю.** Драйвер сам `wait`-ить дочірні процеси;
  скіл/викликач не повинен опитувати статус ззовні.
- **Рій заради «виглядає паралельно».** Якщо `D==true` чи `S==true`, рій
  паралелить те, що насправді послідовне чи спільне — результат гірший і
  дорожчий за ланцюг.
- **Локальні лейни (Tier 0) на задачі, що вимагає судження.** `J==true` ->
  Tier 1 (Haiku), Tier 0 лише коли `J==false` і `T` малий.

## 9. Доставка

Fan-in гілка `cc/<id>/fanin` — джерело правди результату рою. Мерж у main —
**завжди руками Марка** (`git merge --no-ff cc/<id>/fanin`), ніколи
автоматично: скіл/драйвер не мержить fanin у main самостійно за жодних умов.

Лейн-гілки (`cc/<id>/<slug>`) — retention 14 днів, потім прибираються
командою (не автоматично, не за розкладом):

```
sh /root/projects/cc-swarm/bin/cc-gc.sh <repo> [--older-than-days N] [--dry-run]
```

Незалежно від того, змержені лейн-гілки чи ні — fan-in гілка вже містить
усе потрібне, тому прибирання безпечне. Гілки, що ще НЕ увійшли в жодну
fanin-гілку і не в main, `cc-gc.sh` не чіпає — лише попереджає в консоль.

## Смоук-тест

`sh /root/projects/cc-swarm/tests/run-all.sh` — повний тестовий набір
(стеля MAXPAR, зупинка по limit, вбивство по LANE_TIMEOUT, старі шляхи
через симлінки), ізольований від прод-стану й прод-БД. Для ручної перевірки
плану без реального спавну: `DRYRUN=1 sh bin/cc-swarm.sh <repo> <plan>
<id>` — валідація/worktree/маніфест без `claude -p`. Маніфест —
`manifest.tsv` у `/root/ops/cc-swarms/<swarm-id>/`.
